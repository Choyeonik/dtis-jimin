# 06. 종합 문서

> 크롬 확장프로그램 — 군 장병 대상 열차 승차권(좌석) 취소표 자동 신청
> 02~05번 문서(워크플로우/요구사항/기능정의/정책)를 하나로 정리한 요약본.

## 1. 프로젝트 개요

- **대상 사이트**: https://www.dtis.mil.kr/m/ — 군 장병 대상 열차(기차) 승차권 예약 시스템으로 추정.
- **목적**: 원하는 날짜·구간의 취소표(빈 좌석)가 나올 때까지 새로고침을 반복 확인하는 수고를 자동화한다.
- **사용자**: 본인 한 명. 크롬 웹스토어 배포 없이 개발자 모드로 직접 설치해 사용.
- **저장소**: GitHub 비공개(private)로 관리. 민감한 값(디스코드 웹훅 URL, 카카오 API 토큰)은 `.gitignore` 처리된 별도 설정 파일에 보관.

## 2. 사이트 화면 구조

| 화면 | 설명 |
|---|---|
| **화면A "탑승신청"** | 탑승일자 입력(`<input type="date">`) + "조회" 버튼 + 조회 결과 테이블(번호/신청여부/잔여석/일자/열차명/출발역/도착역). 날짜 입력과 결과 테이블이 한 화면에 있음. |
| **화면B "안내" 팝업** | 화면A에서 조건에 맞는 행의 "예약가능"을 클릭하면 뜨는 이용 안내 문구. "확인" 버튼만 있음. |
| **화면C "잔여석예약"** | 탑승일자/노선명/차종/열차명(자동 표시) + 승차역/하차역 드롭다운 + 내부 "잔여석예약" 표(선택 버튼/호차/좌석/출발역/도착역) + "새로고침"/"좌석신청" 버튼. |

## 3. 전체 자동화 흐름

사용자는 크롬 툴바 아이콘을 눌러 **사이드 패널**을 열고, 신청 대상 슬롯(최대 2개, 각각 날짜/출발역/도착역/오전·오후)을 입력한 뒤 "시작" 버튼을 누른다. 로그인은 미리 수동으로 해둔 상태여야 한다.

슬롯 1건당 반복되는 흐름:

1. **(화면A)** 슬롯의 날짜를 입력하고 "조회" 클릭 → 결과 테이블이 채워짐.
2. **(화면A)** 결과 테이블에서 출발역·도착역·오전/오후 조건에 맞는 행을 찾아 "예약가능" 클릭. 조건에 맞는 행이 여러 개면 아무거나 하나, 하나도 없으면 사이드 패널에 경고 표시.
3. **(화면B)** 안내 팝업의 "확인" 클릭.
4. **(화면C)** 승차역/하차역 드롭다운에 슬롯의 출발역/도착역과 동일한 값 선택.
5. **(화면C)** 내부 "잔여석예약" 표는 평소 비어 있음 → "새로고침" 버튼을 260~300ms 사이 난수 간격으로 계속 클릭.
6. 표에 좌석이 뜨면 아무거나 하나 "선택" → 호차/좌석 값이 자동으로 채워짐 → "좌석신청" 클릭 → confirm 대화상자 "확인".
7. **성공 시**: 디스코드 웹훅 + 카카오톡 나에게 보내기로 완료 알림. 슬롯이 더 있으면 "이전" 버튼 2번 클릭으로 화면A로 돌아가 다음 슬롯을 같은 방식으로 진행.
8. **실패 시**("다른 사람이 먼저 선택했습니다" alert): 화면C에 그대로 머무르므로 5번(새로고침)부터 즉시 재시도.
9. 등록된 모든 슬롯이 끝나면 자동화 종료.

언제든 사용자가 "중지" 버튼을 누르거나, 대상 탭이 이동/종료되면(이 경우도 알림 발송) 자동화는 즉시 멈춘다. 실행 중에는 PC가 절전 모드에 들어가지 않도록 막는다.

## 4. 핵심 결정 사항 요약

- **새로고침 간격**: 260~300ms 난수, F5/브라우저 리로드가 아닌 화면 내 "새로고침" 버튼 클릭.
- **신청 가능 시점**: 승차 희망일 이틀 전 낮 12:00부터(그 이후 시간 제한 없음). 정각 자동 시작 기능은 채택하지 않음(수동 "시작").
- **알림**: 디스코드 웹훅 + 카카오톡 나에게 보내기 동시 사용(카톡 단독은 푸시 누락 우려로 이중화).
- **confirm/alert 자동 처리**: `window.confirm`/`window.alert` 오버라이드 방식 채택(디버거 프로토콜 방식 대비 권한·UX 부담 적음). alert 메시지 텍스트는 읽어서 실패 사유 판별에 사용.
- **UI**: 팝업이 아닌 Chrome 사이드 패널. 슬롯 입력값은 패널을 닫았다 열어도 유지되나, 확장/브라우저 재시작 시 초기화.
- **리스크 관리**: 계정 제재 가능성은 감수하고 사용, 별도 자동 중단 안전장치는 두지 않음.
- **완료 여부 표시**: 자동화 성공 시에만 자동 갱신, 수동 완료 처리 기능은 범위에서 제외.

## 5. 남은 미해결 항목 (구현 단계에서 확인)

- `.mil.kr` 사이트 이용약관/보안정책상 이 자동화가 허용되는지 확인 필요.
- 260~300ms 새로고침 속도의 실제 차단(rate limit/봇 탐지) 위험은 실측 테스트로 확인 필요.
- 화면C 내부 "잔여석예약" 표가 "비어 있음"을 코드로 판정하는 방법(DOM 구조)은 실제 사이트 HTML을 보고 구현 단계에서 확정.
- `window.confirm`/`window.alert` 오버라이드가 사이트에서 탐지될 가능성은 낮아 보이나, 실제 테스트로 최종 확인 필요.
- 사이트 페이지가 열려 있지 않은 상태에서 "역 목록 읽어오기"를 눌렀을 때의 처리(안내 메시지 등) 확정 필요.
- 예시 설정 파일(`config.example.js`) 작성 여부, Chrome 확장 권한 목록 최소화 검토.

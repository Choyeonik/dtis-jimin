# 02. 워크플로우 기획 문서

> 크롬 확장프로그램 — 군 장병 대상 열차 승차권(좌석) 취소표 자동 신청

## 1. 배경 및 목적

- 대상 사이트: https://www.dtis.mil.kr/m/ (.mil.kr — 군 관련 사이트)
- 출발역/도착역 개념이 있는 것으로 보아 군 장병 대상 열차(기차) 승차권 예약 시스템으로 추정됨. "좌석신청"은 원하는 날짜/구간의 취소표(빈 좌석)가 뜨면 선점하는 방식.
- 목적: 원하는 날짜의 좌석이 나올 때까지 새로고침을 반복 확인하는 수고를 자동화한다.

## 2. 현재 업무 흐름 (As-Is)

- 사람이 직접 새로고침을 반복하며 좌석 목록을 확인하다가, 좌석이 뜨면 선택 → 좌석신청 버튼 클릭 → confirm 대화상자 확인의 과정을 거친다.
- 로그인은 자동화 대상이 아님 — 사람이 미리 직접 로그인해두고, 그 로그인된 상태에서 확장프로그램을 실행하는 것을 전제로 함.
- 가정: 로그인 세션은 자동화 실행 중 만료되지 않는다고 가정하고 진행함(세션 만료 처리는 범위에서 제외).

## 3. 자동화 대상 반복 작업

- 특정 사이트에서 새로고침을 계속하다가, 원하는 좌석이 나오면 선택하는 자동화.
- 새로고침 방식: 브라우저 새로고침(F5/페이지 리로드)이 아니라, 화면에 있는 "새로고침" 버튼을 클릭하는 방식.
- 판별 기준: 평소에는 좌석 목록이 비어 있고, 좌석이 나오면 그 목록에 항목이 생긴다. 즉 "목록이 비어 있다가 항목이 하나라도 생기는 시점"을 감지하는 방식.
- 목록에 여러 좌석이 동시에 뜰 수 있으며, 그중 아무거나 하나만 고르면 된다(특정 조건으로 필터링할 필요 없음).
- 새로고침 간격: 260~300ms 사이 난수(랜덤)로 매번 다르게, 그 간격마다 새로고침 버튼을 클릭.
- 신청 가능 시점: 승차 희망일 이틀 전 낮 12:00부터 신청 가능(그 이후로는 시간 제한 없이 계속 가능). 예: 2026.09.18 승차분 → 2026.09.16 12:00부터 신청 가능.
- 정각 자동 시작 기능은 검토했으나 채택하지 않음(`chrome.alarms`로 기술적으로는 가능하나, PC가 켜져 있고 절전모드가 아니어야 하는 전제조건이 있음) → 사용자가 직접 "시작" 버튼을 누르는 방식으로 진행.
- 종료 조건: 등록된 대상(최대 2건)의 신청이 모두 끝나면 자동화가 종료된다.

## 4. 목표 흐름 (To-Be)

결제 시스템은 없음(구매가 아니라 "좌석 신청" 개념). 신청 대상은 옵션으로 최대 2건까지 등록 가능(서로 다른 날짜).

**조작 방식:** 툴바 아이콘 클릭 → 팝업이 아니라 사이드 패널(Chrome Side Panel)로 UI가 열림 → "시작" 버튼을 누르면 자동화가 진행됨.

**사이드 패널 입력 항목** (신청 대상 슬롯 최대 2개, 슬롯마다):

- 날짜 입력칸
- 출발역 선택칸
- 도착역 선택칸
- 완료 여부 표시칸 — 자동화가 해당 슬롯의 신청을 성공적으로 마치면 자동으로 "완료"로 바뀜. (수동 완료 처리 기능은 검토 후 범위에서 제외하기로 결정 — 구현 복잡도 대비 실익이 적음.)

**대상(날짜) 1건당 반복되는 흐름:**

1. 캘린더 형식의 날짜 입력 폼(`<input type="date">`)에서 신청할 날짜를 고르고 "조회" 버튼을 누른다.
2. 새로고침을 반복하다가 좌석 목록이 뜨면(빈 목록 → 항목 발생) 그중 하나를 선택(클릭)한다.
3. 화면 오른쪽 아래의 "좌석신청" 버튼을 누른다.
4. 브라우저 기본 확인(confirm) 대화상자가 뜨면 "확인"을 누른다.
5. 알림이 온다(신청 완료 통지) — **디스코드 웹훅 + 카카오톡 나에게 보내기, 두 채널을 동시에 사용하기로 결정.**

**대상이 2건일 때:**

6. 첫 번째 대상(날짜) 신청이 끝나면, "뒤로가기"(브라우저 자체 뒤로가기 `history.back()` 또는 사이트 내 "뒤로" 버튼 클릭 — 둘 다 가능)로 날짜 선택 화면(1번)으로 돌아간다.
7. 두 번째 날짜를 골라 1~5번을 동일하게 반복한다.
8. 등록된 모든 대상의 신청이 끝나면 자동화가 종료된다.

**실패 처리:** 신청이 실패하면(다른 사람이 먼저 선택한 경우 등) 브라우저 기본 alert 팝업으로 안내가 뜸 → 이 경우 해당 슬롯은 알림 없이 2번(새로고침)부터 다시 재시도한다.

## 5. 제약사항 및 고려사항

- 카카오톡 "나에게 보내기"는 기기/알림 설정에 따라 실제 푸시 알림이 뜨지 않을 수 있다는 우려가 있었음 → 디스코드 웹훅을 함께 사용해 이중화하기로 결정.
- 접속 환경 확인 완료: 개인 PC/개인 인터넷망에서 크롬으로 정상 접속 가능한 사이트임(군 내부망 전용 아님).
- 검토했으나 채택하지 않은 알림 대안: 텔레그램 봇(무료, 안정적이지만 카톡+디스코드로 충분하다고 판단), 크롬 데스크톱 알림 병행(PC 앞에 있을 때만 유효), 문자 SMS(유료).
- 취소표가 언제 나올지 몰라 자동화가 장시간(몇 시간) 걸릴 수 있음 → 자동화 실행 중에는 `chrome.power` API로 PC 절전을 막는 기능을 넣기로 결정.

## 6. 미해결 질문 / 제안

- [제안] 대상 사이트가 `.mil.kr` 도메인이므로, 자동 새로고침·자동 클릭이 사이트 이용약관/보안정책에서 금지되어 있지 않은지 확인이 필요함 — 본인 계정으로 본인 업무(좌석 신청)를 자동화하는 것이라도, 군 시스템은 일반 상용 사이트보다 자동화·매크로 사용에 민감할 수 있음.
- [제안] 새로고침 간격(260~300ms, 초당 약 3~4회)도 여전히 빠른 편이라 사이트의 rate limit이나 봇 탐지에 걸려 일시적/영구적으로 차단(계정 제재 포함)될 가능성이 있음 — 실제 운영 전 짧게 테스트해보는 것을 권장.
- **[확인 예정]** "목록이 비었다"를 코드로 어떻게 판정할지는 실제 사이트 HTML 구조를 봐야 확정 가능함 — 특정 DOM 요소의 개수(0개 여부), "없음" 문구 유무, API 응답의 빈 배열 여부 등 사이트 구조에 따라 감지 방식이 달라짐. 구현 단계에서 실제 페이지를 함께 확인하고 다시 논의하기로 함(사용자 요청 사항).
- confirm/alert 자동 처리 방식: 두 가지 방법을 비교한 결과, **`window.confirm`/`window.alert` 오버라이드 방식**을 우선안으로 채택. (근거는 아래 "기술 검토 메모" 참고)

### 기술 검토 메모 — confirm/alert 자동 처리 방식 비교

- **방법 A: `window.confirm`/`window.alert` 오버라이드** — 페이지가 로드되기 시작할 때(`document_start`, MAIN 월드) 확장프로그램이 `window.confirm`/`window.alert`를 자체 함수로 미리 바꿔치기해서, 네이티브 대화상자 자체가 뜨지 않고 곧바로 원하는 값(확인=true)을 반환하도록 만드는 방식. 추가 권한(`debugger`)이 필요 없고, 사용자에게 "이 브라우저가 디버깅되고 있습니다" 같은 경고 배너도 뜨지 않음. confirm은 "좌석신청" 버튼 클릭 같은 사용자 동작 이후에 호출되므로, 페이지 로드 초기에 미리 오버라이드해두면 타이밍 문제 없이 안정적으로 작동함.
- **방법 B: 크롬 디버거 프로토콜(`chrome.debugger`)로 브라우저 자체 제어** — 실제로 뜬 네이티브 대화상자를 감지해서 `Page.handleJavaScriptDialog`로 자동 확인 처리. 어떤 경로로 다이얼로그가 뜨든 확실하게 잡아낼 수 있지만, `debugger` 권한이 필요하고 브라우저에 "확장프로그램이 이 브라우저를 디버깅 중입니다" 배너가 계속 떠서 사용 경험이 나빠짐.
- **결론:** 이번 케이스는 confirm/alert가 항상 사용자의 명시적 클릭(좌석신청 버튼) 이후에만 발생하므로 타이밍 리스크가 낮음 → 배너 없이 깔끔하게 동작하는 **방법 A(오버라이드)**를 우선 채택. 구현 중 안정성 문제가 확인되면 방법 B로 전환을 검토.
- **주의사항 1 (탐지 가능성, 낮음):** 극히 일부 사이트는 `window.confirm.toString()` 등으로 네이티브 함수 변조 여부를 검사하기도 함 — dtis.mil.kr에서 이런 탐지를 할 가능성은 낮아 보이나 100% 배제할 수는 없음.
- **주의사항 2 (필수 반영):** `alert`를 무조건 무시하면 "이미 신청됨" / "다른 사람이 선점함" / "시스템 오류" 같은 서로 다른 실패 메시지를 구분할 수 없게 됨 — 오버라이드 함수 안에서 alert에 전달된 메시지 텍스트를 읽어 상황을 판별한 뒤 무시하도록 구현해야, 앞서 정한 "실패 시 재시도" 로직이 정확히 동작함.
- **사전 검증 방법:** 변조 탐지 여부는 사이트 JS 소스(개발자도구)에서 `window.confirm.toString()` 류의 탐지 코드가 있는지 확인하고, 구현 후 실제로 한 번 테스트해서 최종 확인한다.
- **대안 검토 — 스크린샷 촬영 후 이미지 분석 + 실제 마우스 이동/클릭:** 검토했으나 채택하지 않음. `confirm()`/`alert()`가 떠 있는 동안 해당 탭의 JS 실행 자체가 완전히 멈추기 때문에, 페이지 안에서 만드는 가짜 클릭 이벤트로는 다이얼로그를 닫을 수 없음. 실제 OS 수준 마우스 제어가 필요해 크롬 확장 밖에 별도 네이티브 프로그램(Native Messaging 연동)이 있어야 하므로 구조가 불필요하게 복잡해짐. 오버라이드가 통하지 않을 경우의 대안은 이 방법이 아니라 **방법 B(`chrome.debugger`)** — 브라우저 프로세스 수준에서 동작해 페이지 JS가 멈춰 있어도 다이얼로그를 처리할 수 있음.
